# Клиенты и суперпользователь

Одна организация — один независимый клиент. Все операционные данные используют
существующий `organizationId`; email пользователя уникален во всей системе.
Суперправа хранятся отдельно от клиентских ролей и не назначаются через UI пользователей.

## Обновление существующей установки

1. Сделать резервную копию PostgreSQL и uploads.
2. Проверить дубликаты email: `SELECT lower(trim(email)), count(*) FROM users GROUP BY lower(trim(email)) HAVING count(*) > 1;`. Разрешить конфликты вручную. Миграция 0043 остановится с перечнем конфликтующих email, не объединяя аккаунты.
3. В окружении приложения задать `SUPERUSER_EMAIL` равным email существующего активного администратора. При старте сервер выдаст ему системные права, сохранив его организацию и клиентские роли. Неверный email останавливает запуск, чтобы ошибка настройки была заметна.
4. Выполнить `npm run db:migrate` (в production — существующим контейнером миграций), затем запустить обновлённый сервер. Миграции 0043 и 0044 добавляют платформу и ограничения клиентских связей. Существующие организации получают статус active.
5. Войти заново: старые cookie не принимаются новым сервером. Суперпользователь попадает в `/system/clients`.

`SUPERUSER_EMAIL` — явное повышение полномочий. Удаление переменной не отзывает уже
выданные права; отзыв выполняется управляемым изменением `users.is_superuser` в БД.
После отзыва следующая проверка сессии использует текущие полномочия из БД.

## Подключение

По умолчанию действует режим «Только по приглашению». Миграция 0047 включает его
и для существующих установок, закрывая ранее открытую регистрацию. В кабинете можно
создать клиента и пригласить первого администратора. Если письмо не отправлено,
клиент остаётся сохранённым, а приглашение можно повторить из меню карточки.

В `/system/settings` можно включить самостоятельную регистрацию. Пользователь
вводит компанию, имя, email и пароль. Компания и активный администратор создаются
только после подтверждения email. Ссылка действует 24 часа и используется один раз;
повторная отправка доступна через минуту. Отключение регистрации запрещает также
подтверждение ранее начатых заявок. SMTP/Brevo и публичный URL приложения должны
быть настроены существующими переменными окружения.

Один email нельзя использовать для нескольких компаний, включая приглашённые и
архивные аккаунты. Активная заявка регистрации резервирует email до истечения ссылки.

## Ключи доступа

После входа кнопка с отпечатком в верхней панели открывает «Ключи доступа».
Пользователь подтверждает текущий пароль и добавляет ключ для своего аккаунта.
На странице входа кнопка «Войти по ключу» позволяет выбрать сохранённый ключ без
ввода email. Устройство подтверждает вход через Face ID, Touch ID, PIN или
совместимый ключ безопасности. Пароль остаётся доступным для входа и восстановления.
Ненужный ключ можно удалить в том же окне после подтверждения действия.

После входа с паролем в поддерживаемом браузере автоматически предлагается создать
первый ключ. Подтверждение пароля используется сразу при входе; повторно вводить
его для этого предложения не нужно. Ключ создаётся только после нажатия
«Создать ключ» и подтверждения на устройстве. «Позже» скрывает предложение для
этого аккаунта на 30 дней в текущем браузере. После входа по ключу и при наличии
хотя бы одного ключа предложение не показывается. Вручную добавить ключ можно
в любой момент; если предложение открыто дольше пяти минут, потребуется снова
подтвердить пароль. Пароль не сохраняется для предложения.

Перед обновлением применить миграцию `0048_passkeys`. `NUXT_PUBLIC_APP_URL` должен
точно соответствовать публичному адресу приложения с HTTPS (для локальной
разработки разрешён HTTP на localhost). Ключи привязаны к домену; смена домена
требует добавления ключей заново. Сервер хранит публичные ключи, а биометрию
проверяет устройство. Запросы подтверждения действуют пять минут, привязаны к
браузеру и используются один раз. Заблокированные и архивные пользователи,
приглашённые аккаунты и заблокированные компании не получают доступ через ключи.
Суперпользователи сохраняют действующие правила доступа к системному кабинету.

## Поддержка и блокировка

«Открыть CRM» выбирает один клиентский контекст в серверной сессии. Операционные
запросы суперпользователя включают ревизию контекста; запросы из старой вкладки
отклоняются. Переключение перезагружает документ и остальные вкладки этого браузера.
Постоянная панель показывает клиента и позволяет вернуться к списку.

Суперпользователь не назначается исполнителем. Его ID сохраняется в операционном
аудите; вход/выход, создание клиента, изменение режима и статуса записываются
в `platform_audit_logs`. Публичная регистрация записывает событие `client.registered`.

Блокировка сохраняет данные, закрывает клиентский доступ и подтверждение приглашений,
исключает клиента из iCal-синхронизации и отправки уведомлений. Запущенная синхронизация
завершает транзакцию перед фиксацией блокировки либо пропускает запись после неё.
WebSocket закрывается сразу в текущем процессе и в течение 5 секунд при проверке
сессии другим процессом. Суперпользователь сохраняет ручной доступ для поддержки.

## Проверка в изолированном PostgreSQL

Обычный `npm test` запускает модульные тесты. Интеграционные тесты используют только
БД с именем `aparts_platform_test`, применяют все миграции и очищают её данные.
Не указывать рабочую БД: тесты намеренно отказываются запускаться с другим именем.

```sh
docker run -d --name aparts-platform-test -e POSTGRES_PASSWORD=platform_test -e POSTGRES_DB=aparts_platform_test -p 127.0.0.1:55439:5432 postgres:17-alpine
PLATFORM_TEST_DATABASE_URL=postgres://postgres:platform_test@127.0.0.1:55439/aparts_platform_test npm test
docker rm -f aparts-platform-test
```
