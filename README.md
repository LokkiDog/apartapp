# Aparts CRM

Mobile-first CRM для управления апартаментами в Банско. Интерфейс на русском, денежные суммы вводятся и хранятся в EUR с точностью до двух знаков, а операционное планирование ведётся по датам без времени.

## Запуск

1. Скопируйте `.env.example` в `.env` и задайте `DATABASE_URL` (по умолчанию локальный порт `55432`), `NUXT_SESSION_PASSWORD`, `BOOTSTRAP_ADMIN_EMAIL` и `BOOTSTRAP_ADMIN_PASSWORD`.
2. Запустите инфраструктуру: `docker compose up -d`.
3. Выполните `npm install`, `npm run db:migrate`, затем `npm run dev`.

Первый администратор создается идемпотентно при старте сервера из переменных окружения.

Локальный Compose-проект `aparts` запускает два PostgreSQL с отдельными томами.
`postgres-aparts` доступен на порту `55432`, а `postgres-magicmop` — на
`127.0.0.1:52951`. Для новой базы MagicMop используйте
`postgres://magicmop:magicmop@127.0.0.1:52951/magicmop` или задайте
`MAGICMOP_POSTGRES_PASSWORD` в `.env` перед первым запуском.

Для примеров статистики выполните `npm run db:seed -- --organization=<UUID>`.
Команда работает только с локальной базой `aparts`; в выбранной организации
должны быть активный администратор и минимум три уборщика. Она добавляет
отдельные объекты с пометкой `[Демо]`, заезды и работы относительно текущей
даты Банско. Существующие данные сохраняются, повторный запуск не создаёт
дубли и не сдвигает даты уже добавленного набора. Уведомления не отправляются.

## Production

Production работает в Docker Compose за host Nginx на отдельном VPS по адресу
`https://crm.aparts-bansko.com`. Образ приложения собирается на Node 22,
PostgreSQL и фотографии хранятся в отдельных Docker volumes, а миграции
выполняются одноразовым контейнером перед запуском новой версии.

Подготовка VPS, DNS, TLS, `.env.production`, внешний SMTP и автоматический
деплой через GitHub Actions описаны в [docs/DEPLOYMENT.md](docs/DEPLOYMENT.md).
Автоматические резервные копии в текущую схему не входят.

## Настройки уведомлений

В профиле пользователь выбирает доставку каждого события в CRM, Push и Email.
По умолчанию CRM и Push включены, Email выключен. Изменения относятся к новым
уведомлениям; история ленты сохраняется. Push дополнительно требует разрешения
браузера и подключения текущего устройства.

Перед запуском этой версии примените миграцию `0049_notification_preferences`
через `npm run db:migrate`. Настройте существующий почтовый транспорт SMTP или
Brevo для доставки Email. Письма обрабатываются сервером каждые 30 секунд,
повторяются при ошибке до пяти попыток; очередь хранится в PostgreSQL.
`notification_email_queue.status = 'failed'` означает исчерпание попыток.
После отключения Email ожидающие отправки письма пропускаются. Запросы смены
пароля, приглашения и служебные события сессии этими настройками не отключаются.

## История обновлений

Страница «Что нового» использует `shared/config/changelog.ts`.
Записи перечисляются от новой к старой, тексты находятся в разделе `changelog`
переводов RU/EN/HE. Версии обозначаются датой `ГГГГ.ММ.ДД`; это номера записей
журнала, а не Git-теги. До публикации используйте статус `upcoming`, после
успешного деплоя меняйте его на `released` и указывайте фактическую дату выпуска.

Для анонса заполните `announcement` (обложка и краткие пункты) и включите
`enabled`. Автоматический попап использует только последнюю опубликованную
версию с анонсом. В черновике доступна кнопка «Посмотреть анонс» без отметки
просмотра. Закрытие опубликованного анонса или чтение журнала сохраняет просмотр
на аккаунте пользователя, независимо от устройства. Небольшие исправления можно
публиковать без анонса. Перед запуском примените `0050_release_announcements`.
При ошибке сохранения попап закрывается, а пользователь получает предупреждение;
в этом случае на другом устройстве анонс может появиться повторно.

## Проверки

`npm run typecheck` — TypeScript и Vue.

`npm test` — правила Zod-контрактов.

`npm run test:e2e` — Playwright-сценарии входа на mobile и desktop. Перед запуском поднимите PostgreSQL, примените миграции и запустите приложение; при другом адресе задайте `E2E_BASE_URL`.

`npm run build` — production build и PWA service worker.

`npm run lint:fsd` — Steiger для границ Feature-Sliced Design.

## Структура

- `app/pages` — тонкие Nuxt route entrypoints;
- `src` — FSD-слои (`app`, `pages`, `features`, `entities`, `shared`);
- `server/modules` — доменные use cases и правила доступа;

### Переписка с гостями

Модуль «Сообщения» выключен по умолчанию. После применения миграций супер включает его в системной карточке нужного клиента. Администратор компании подключает собственного Telegram-бота в «Настройки → Сообщения». Бот закрепляется за компанией, повторное подключение использует того же бота и сохраняет историю.

Для сервера задайте `NUXT_MESSAGING_ENCRYPTION_KEY` — 32 случайных байта в hex (`openssl rand -hex 32`) — и публичный HTTPS-адрес `NUXT_PUBLIC_APP_URL`. Ключ необходимо сохранять между перезапусками и вместе с резервной копией БД, чтобы расшифровывать сохранённые токены. Файлы используют существующий `FILE_STORAGE_PATH`. Внешний адрес `/api/messaging/telegram/:id/webhook` должен принимать запросы Telegram.

При отключении модуля приём и отправка прекращаются, ожидающие исходящие отменяются, история сохраняется. Сообщения периода отключения не импортируются. Гость должен сначала открыть бота и нажать «Начать». Админ вручную связывает диалог с заездом. Telegram подтверждает отправку через API, сведения о прочтении гостем не предоставляются.

Изолированные PostgreSQL-тесты запускаются через `MESSAGING_TEST_DATABASE_URL=postgres://…/aparts_messaging_test npx vitest run tests/messaging-postgres.spec.ts`. Они очищают исключительно БД с именем `aparts_messaging_test` и применяют все миграции.

### Запуск production через Docker Compose

Файл `.env.production` рядом с `docker-compose.prod.yml` содержит настройки контейнеров и значения для подстановок в YAML. Production-файл подключает сервисы через `include` и загружает этот env-файл автоматически. Для Aparts требуется Docker Compose 2.20+, для переопределений MagicMop — 2.24.4+.

```bash
docker compose -f docker-compose.prod.yml up -d
docker compose -f docker-compose.prod.yml down
```

После изменения кода используйте `up -d --build`. При обновлении схемы отдельно применяйте миграции существующим процессом деплоя. Значения из окружения оболочки и корневого `.env` имеют приоритет над значениями `include.env_file`; на production храните настройки в `.env.production`, не дублируя их в `.env`.

MagicMop запускается отдельной командой `docker compose -f docker-compose.magicmop.yml up -d`. `APARTS_ENV_FILE` позволяет выбрать другой файл окружения. Скрипты деплоя продолжают использовать явный env-файл и изолированные имена проектов.

`npm run check:compose` проверяет обе конфигурации с тестовыми переменными, без запуска контейнеров. Проверка входит в GitHub Actions, включая push в `main`; автоматический production-деплой запускается только для веток `aparts` и `magicmop`.
